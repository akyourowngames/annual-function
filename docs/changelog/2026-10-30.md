## 1. Security audit — the "code alone opens the family" hole

**What was wrong.** An invitation code is printed paper and gets shared. The app
had added a 6-digit code sent to the family's phone, but the phone it went to
could be claimed by anyone who knew three things a classmate can find out:
admission number, full name, and class.

So: know the three details → chat the bot → your own phone is saved as "the
family's phone" → the 6-digit code arrives on your phone → you open the family's
ticket and see their guest list and QR pass.

**Fixed.**

- Only a phone the school checked by hand can receive the 6-digit code now.
  (`lib/security/family.ts`, one rule, in one place.)
- The QR pass is never sent by chat unless the school checked the phone.
  If unsure, it is not sent.
- Bulk "send passes" no longer sends the QR pass to an unchecked phone.
- Added **Verify a family** in `/admin` so staff can actually check phones.
- New database script `0012_data_api_lockdown.sql` locks the database tables so
  a leaked browser key cannot read tickets directly.

**Tests:** 106 pass. Three new test files.

## 5. The limit that could be dodged by moving

**What was wrong.** The "only a few tries" guard counted the caller's network
address. Change phone, change wifi, change network — the count starts again at
zero. The rule said "5 tries per person" but actually meant "5 tries per
address", and addresses are free.

**What that did and did not do.** It did **not** let anyone in. Six digits is
1,000,000 possible numbers; a few dozen tries still cannot guess it. What it did
allow was **cost and nuisance**: lots of paid messages, and a real family's
phone buzzing with codes they never asked for.

**Fixed.** The two limits that matter are now tied to the **family** and to the
**whole school**, so no change of phone or network resets them:

| Limit | Counted on | Value |
|---|---|---|
| Messages per family per day | the family | 8 |
| Messages for the whole school per day | the event | 600 |
| Wrong guesses per family per day | the family | 25 |

Two details that make it correct rather than annoying:

- The counter only moves when a message is **actually sent**. Repeatedly poking
  the button during the 60-second wait does not spend a family's allowance.
- A blocked caller gets the same plain "contact your class teacher" message as
  everyone else, so a flood learns nothing about whether a code exists.

The network-address guard is still there, but only as a flood net against one
machine hammering the page. It is clearly commented as not being the real
control.

**Tests:** `otp-limits-test.mjs` (6 checks) proves the keys are family-based,
that different families count separately, that a school-wide ceiling exists, and
that cooldown hits do not spend the allowance.

## 13. Made replies fast (5.4s → 1.2s for common questions)

**The complaint.** Telegram replies felt slow.

**What I measured instead of guessing.** Timed the app and the gateway
separately:

| What | Time |
|---|---|
| Database query (full-text search) | **0.1 ms** — not the problem |
| Model call, tiny prompt | 1.1–1.4 s |
| Model call, 12k-char prompt | 3.6 s |
| Whole app reply, end to end | **5.4–9.9 s** |

So the database was innocent and the model was only part of it. Three separate
costs were stacking up.

### Cost 1 — the model itself

`kilo-auto/free` was still in the fallback list. It is a **reasoning** model: it
returns `content: ""` and hides the answer in `reasoning_content`, which this
app never reads. It also took **12.5 s** before we discovered that, then fell
through to the next model. Removed from the chain entirely.

Champion, measured over 5 runs each:

| Model | Answered | Average | Worst |
|---|---|---|---|
| `kilo-auto/small` | 5/5 | **1.2 s** | 1.4 s |
| `cohere/north-mini-code:free` | 5/5 | 1.7 s | 2.6 s |
| `reflection/beam-free` | **4/5** | 1.6 s | 2.0 s |

`beam-free` missed one answer in five — a family would get nothing. Promoted
`kilo-auto/small` to default, with the two others as backup.

### Cost 2 — the retry timeout

`perAttempt` was 12 s. One bad model could burn 12 seconds before the next was
tried. Cut to 8 s, which is still six times the healthy response time.

### Cost 3 — prompt size

Five documents × 6,000 chars, plus 2,000 chars per knowledge chunk, was pushing
up to ~30k characters into **every** message. Trimmed to 1,200 chars per
document and the top 3 chunks at 900 each — plenty for the matched passage,
without the bulk.

### The real win — don't call the model at all

Venue, dress code, parking, entry and date were already stored as plain text in
`event_settings`. Paying a model to restate them costs seconds for zero benefit.

Added `instantAnswer()`: it answers those directly, **before** the model, and
only when two things are true — the question is a clean match for exactly one
topic, and the school actually published that field.

**Result:** 5.4 s → **1.2 s** for those questions. Types "typing…" in Telegram
while it thinks (`sendChatAction`).

**Two bugs the tests caught in my own new code:**

1. "where can i park" matched *both* parking and the generic "where" word, so it
   fell through to the slow path. Fixed: a solitary specific topic absorbs
   generic question words.
2. Then it over-corrected: "venue and dress code" matched dress code and
   answered **only half the question**. Fixed: generic words are only absorbed
   when the text uses a *question* word (where/when), not a real topic word
   (venue/place/date). Two genuine topics now always go to the model.

That second one matters — a wrong instant answer is worse than a slow correct
one.

### Honest limit on the numbers

Only `venue` is published in your database right now. Date, dress code, parking
and entry are all null, so those questions **correctly** still take 6–8 s — the
fast path refuses to invent an answer. Fill those four fields in
`/admin` → Event settings and every one of those questions drops to ~1.2 s.

**Tests:** 119 pass (was 112). New `instant-answer-test.mjs` (7 checks) locks the
guard rails: greetings, two-topic questions, unpublished fields and long
messages must all reach the model.

## 14. I hardcoded replies. That was wrong. Removed.

**What I did wrong.** To make replies faster, I wrote a table of words mapped to
fixed answers: if the message contains "venue", return the venue sentence. If it
contains "dress", return the dress sentence.

That is **not an assistant**. It is a list of if-statements wearing an
assistant's coat. It would have broken the moment a family asked something
slightly different, asked in Hindi, or asked two things at once.

**I deleted it.** `INSTANT_TOPICS` and `instantAnswer()` are gone, along with the
test that only existed to check the hardcoded table.

**Removed a second one too.** The "AI unavailable" path also picked an answer by
matching words in the question. Now, when there is no model, it prints the
school's own published fields and says plainly the assistant is unavailable.
It never guesses.

**What replaced it — the correct shape, copied from `copilot-chat`:**

1. **One guidance prompt** — who the bot is, how to behave, what to answer from,
   what never to invent. Written once, at the top of `answerQuestion`.
2. **Tools** — `get_invitation`, `search_event_information`, `list_my_guests`,
   `check_ticket_status`, `set_rsvp`, `escalate_to_staff`. The **model** decides
   which to call.
3. **The model writes every word**, in whatever language the family used.

**And I found the honest speed fix.** Documents and knowledge chunks were being
fetched on *every* message — a full-text search plus a knowledge search before
the model was even called, even for "hi". Now only the event settings are
fetched up front; the model calls `search_event_information` when the question
actually needs it. Faster **and** more agentic — the model decides.

**Proof every reply now comes from the model:**

| Question | Reply |
|---|---|
| where is the venue | "The venue for the Annual Function is the **School Ground**. 🏫" |
| what is the dress code | "I'm sorry, I don't have information about a specific dress code…" |
| when is the function | "I'm sorry, I don't have the exact **date** or **start time**…" |
| greeting | "Hello! Welcome to the Annual Function 2026 helpdesk. 🌟" |

Note the second and third: the model **admits it does not know** instead of
inventing. A hardcoded table would have confidently printed a wrong answer.

**New guard so this cannot happen again.** `no-hardcoded-replies-test.mjs` reads
the source and fails if a keyword→reply table returns, if the model stops
getting a guidance prompt, or if the tools disappear. I checked it actually
works by putting a hardcoded table back temporarily — the guard failed, as it
should, then I restored the file.

**Written into `AGENTS.md` as Rule 7**, in the same spirit as
`copilot-chat/AGENTS.md` §1 "No Hardcoding — Ever".

**Honest cost.** Replies are back to **3–7 seconds** instead of 1.2 s, because
the answer genuinely comes from the model now. The right way to make that faster
is a faster model or filling in the event fields — not a lookup table.
