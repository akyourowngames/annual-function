## 1. Ticket passes can expire now

**What was wrong.** A ticket QR code worked forever. Once it was printed or sent,
it opened the gate on any day, at any hour. The only way to stop one was for a
staff member to switch that one family's invitation off, or to give them a brand
new code. So after the function was over, every pass in the school still said
"Entry pass", and the gate still let people in.

**What it means for you.** You now have one switch for the whole evening: pick
the time the doors close. After that moment, every ticket is refused at the gate
and the screen says plainly that the pass has expired.

It changes nothing until you pick a time. Empty means "never expires", which is
exactly how the app worked before. So it is safe to add now.

**What changed.**

- One new setting in `/admin` → **Event settings** → *Passes stop working at
  (optional)*. Pick a date and time. Clear it to re-open the gate.
- The gate scanner refuses an expired pass and shows the reason in words, not a
  blank "invalid". A new pass and a closed pass now look different on screen.
- The family's ticket says **"Valid until …"** while it works. When it has
  closed, the QR is replaced by the sentence explaining why, and printing or
  downloading the pass is switched off.
- The family's invitation badge follows the same three states: `valid`,
  `expired`, `inactive`.
- One rule decides all of this — `web/lib/passes/expiry.ts` — so the screen and
  the database can never disagree about a pass.
- The check happens **inside the database save** that records the entry, not only
  on the screen. An old page, a second staff phone, or a double tap cannot slip a
  guest in after the gate closed.
- Database step: `drizzle/migrations/0014_pass_expiry.sql`. It only adds one
  empty column. See `docs/security/RUN-THIS-SQL.md` §6.
- New test: `cd web && npm run test:passes` — 9 checks on the rule.
- The end-to-end script (`npm run test:e2e`) now also checks that an expired pass
  reads as closed and cannot enter.

**Design note, so nobody is surprised.** The expiry is one moment for the whole
event, not one per family. A school function has one closing time, and a single
field is something the office can actually set. Per-family expiry does not exist.

**What is still not done.**

- **The database change has not been applied.** You must run
  `node scripts/migrate.mjs drizzle/migrations/0014_pass_expiry.sql` in `web/`
  before the new setting can save anything.
- **I did not test the gate against a real database.** There is no database key
  in this folder, so the end-to-end script could not run. The rule itself is
  tested; the road from the scanner to the database is only typechecked.
- An expired pass still lets the family open their portal and see their guest
  list. Only the gate is closed. If you want the whole portal to close too, that
  is a separate change.
- The reminder messages and WhatsApp/Telegram pass sending do not mention the
  expiry date yet.

## 2. The closing-time checks now run on GitHub

**What changed.** The nine small checks for pass expiry now run whenever a pull
request is checked. The live test also puts the old closing time back if the
test stops early. While the gate saves a guest's entry, a staff change to the
closing time waits its turn. The gate will not save an entry using an old time
after a newer closing time is set.

**What it means for you.** The door test is less likely to leave the whole event
closed by mistake. The automatic checks will cover the new rule each time this
change is sent for review.
